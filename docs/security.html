The key is written into the page only when opened on the laptop itself; any other browser enters it once. Both pages set a Content-Security-Policy that forbids sending it anywhere but this server.

04The MQTT broker requires a passwordPass · limitation

Mosquitto uses password authentication; anonymous and wrong-password clients are refused. The traffic itself is not encrypted — see Limitations.

05The AI can never issue a hardware commandPass

Device commands come only from fixed, server-side lists — never from model output. The panel can send a short whitelist with server-chosen parameters; the developer page only actions a device advertises, capped at 2 KB. Self-update and emergency-stop are unreachable from either page.

Limitations & what is not claimed

  • Self-verification, not a third-party audit. Every check is reproducible (commands below), but no external party has reviewed it.
  • MQTT is unencrypted on the LAN. The broker password is sent in the clear, so a sniffer on the same Wi-Fi could read it. Acceptable on a trusted home network; add TLS (port 8883) before an untrusted one.
  • No emergency-stop on any device. Fine today — the devices have no motors (LEDs, buzzer, screens, a camera). A hardware kill switch and a device-side watchdog are required before any actuator is added.
  • Failure cases untested: broker restart, Wi-Fi loss, Pi power loss. The agent-crash and station-restart cases are verified.
  • Exposure assumption: nothing is port-forwarded to the internet. The controls hold for a LAN; internet exposure would need more (rate limiting, TLS everywhere, stronger key handling).
